# Bounded security and restore-design review

Reviewed 16 October 2026 against independently authored Dualscan engine/WordPress PHP, the sealed runtime guard, deployment consent flow and host-route configuration. This was a read-only review of the implementation. This is not a penetration test, complete security audit, production certification or a guarantee of recovery from process/host failure. Runtime qualification belongs to the separate verification records.

## Review status

The original source manager remains an owner-controlled authoring interface. Every normal restored target defaults to a sealed public application: no WordPress web administration or web login is available to the former owner or any other account. The encrypted source image remains the authoring snapshot; deployment deliberately changes the restored copy's principal records, sessions and bootstrap policy.

The factory/image-format, sealed-deployment, account-removal, consent-plan, host-route and 1.0.1 server-managed-key reviews are complete as bounded static reviews. Reported defects listed below were corrected and re-read. No remaining blocking defect was identified in the reviewed supported paths. This conclusion does not replace the separate native runtime evidence, certify arbitrary plugin code or qualify the supplied container configuration as executed.

## Issues reported and corrections reviewed

1. **Storage permissions and web exposure — corrected.** The initial implementation altered pre-existing directories and ignored chmod failure. `class-safe-files.php`, `privateDirectory` now rejects filesystem root, writable directories with group/world access and, when POSIX identity is available, directories not owned by the PHP worker. It does not change permissions on existing directories. `class-plugin.php`, `storage` uses this guard and rejects canonical containment within both ABSPATH and the server-provided DOCUMENT_ROOT. Administrators must still ensure the chosen path is not exposed by another virtual host, alias or external file-serving rule.
2. **Restore writer coordination — corrected within the declared operator contract.** `class-plugin.php`, deployment/job-start guards now require explicit stopped-writer acknowledgment for create and restore. Before the first mutation, its `class-plugin.php` / `runJob` progress callback creates an exclusive WordPress maintenance marker, after authentication and rollback-image validation. The marker is preserved through restoration and controlled rollback. The wrapper removes only the exact marker it owns after success/controlled rollback; rollback-failure code 1001 retains maintenance. Engine catchable rollback honors the same preservation policy in the `class-image-manager.php` / `restore` exception path. External writers still require operator suspension; hard process termination remains a manual recovery case.
3. **Managed-plugin scope — corrected/qualified.** Custom plugin menu entries and `?page=` administration screens are now hidden/denied for nonowners, alongside core plugin management and manage_options. This does not promise to repair a third-party endpoint with missing or inappropriate authorization, conceal source code from the host administrator or isolate hostile code in the same PHP process.
4. **First activation self-denial — corrected.** Adding manage_options denial initially caused the first activating administrator to fail the plugin's own capability check before an owner was stored. `class-managed-access.php`, `activate` now requires an authenticated user with underlying administrative manage_options membership for that initial assignment. Recovery uses the same underlying capability view in `isOwner`, avoiding recursive map_meta_cap checks. Runtime fresh-activation testing remains the independent confirmation.

## Version 1.0.1 server-managed encryption

The public installed plugin-folder basename supplies a normalized **context**, not a secret password or encryption entropy. A random 32-byte server master is retained in private external storage. HKDF-SHA256 derives a folder-specific high-entropy secret; the unchanged authenticated image codec further derives its per-image AES key using the random salt and bounded PBKDF2 parameters. Renaming an archive cannot supply the missing server key or change the installed package context. The random master and derived secret are never embedded in the plugin or image.

| Key lifecycle | Static checks |
| --- | --- |
| Creation | `ServerKeyring::resolveOrCreate` creates missing random material only for explicit initialization/backup. A keyring lock serializes concurrent creation, and exclusive creation plus hash readback avoids silent overwrite or partial-key acceptance. |
| Opening images | Inspection and restore use `requireExisting`. Missing or wrong-server keys fail; opening an image never silently generates a replacement key. Wrong key/folder causes GCM authentication failure before public target mutation. |
| Context/path | Package basename is bounded, normalized and rejects separators/traversal. It maps to a fixed private key filename rather than a path taken from an image header. Folder binding occurs in the HKDF context; the image's existing complete header remains authenticated by GCM. |
| Private location | Keyring storage is outside the supplied canonical public roots. Directories require owner-only permissions and effective ownership when available; raw key files must be regular, nonsymlink, readable, exactly 32 bytes and mode 600. Existing unsafe/general directories are rejected without broad chmod. |
| Web authority | Installed package basename and server private storage are selected by code/server configuration. Client job fields cannot choose a raw key, key path, password or arbitrary package folder. Key status exposes only a nonsecret identifier. |
| CLI provisioning | Normal `bin/dualscan.php` key mode and `bin/keyring.php` require an existing DUALSCAN_PUBLIC_ROOT and also exclude the package tree; backup/restore additionally exclude site roots. Explicit private key-file provisioning never replaces a different existing key. |
| Key backup | Export uses a fresh mode-600 raw file in a dedicated private directory, refuses public paths and refuses existing destinations. Import checks the same privacy/type/size rules. Neither command prints raw key bytes. |
| Compatibility | Explicit offline `--password-mode` remains for earlier password-encrypted images; it is not a web password prompt or an automatic fallback. It requires the operator's legacy environment secret. |

The server key is intentionally **outside** the captured website/image. Transfer its private backup separately to a destination using the same normalized package-folder context. A complete site image alone cannot recover a lost server key. Keep durable key backups alongside an operator recovery procedure; ephemeral temporary storage is unsuitable as the only long-term key location. The supplied code performs best-effort in-memory wiping of raw key buffers, not a guarantee against memory forensics, swap, privileged PHP code or host snapshots.

### Additional defects corrected during this pass

- Guard initially checked only the executing script's basename, allowing another plugin index.php; it now requires the canonical root front controller.
- A guard installed solely in the default MU directory could be skipped by custom captured configuration; the early trusted config include now executes independently.
- Config patching initially risked breaking leading strict_types, widening wp-config permissions and embedding a nonportable host path; token-aware insertion, permission preservation and relative require fix those cases.
- Explicit offline authoring recovery initially deleted the guard while retaining its config require; it now strips only the managed token-marked bootstrap before removing policy files.
- Rollback initially lacked opcache invalidation for restored bootstrap files; copied and removed paths now invalidate available cached code.
- Administrative-user deletion initially could cascade unknown plugin content through foreign keys; unsupported inbound dependencies are now refused before deletion, with the outer rollback path preserved.

The deployment agreement is versioned draft product text, not a legal enforceability opinion. The technical checks bind the displayed agreement version to the accepted plan. The text expressly preserves applicable GPL/open-source, non-waivable and lawful statutory rights; software checks cannot determine whether every clause is enforceable in every jurisdiction.

## Limits and operating assumptions

- On the original authoring site, a nonowner account retaining broad administrator powers such as theme/PHP editing or owner-account administration remains a trusted operator; use least-privilege client roles. On the sealed restored site, all WordPress web authentication/administration is disabled and administrative principals are removed.
- Only deploy trusted, authorized PHP application images. Sealing does not sandbox malicious plugins or remove pre-existing application vulnerabilities. An encrypted archive protects its contents at rest; it does not protect against a compromised web runtime, privileged plugin, filesystem administrator or server root. Managed plugin UI restrictions are not isolation between mutually hostile code sharing a WordPress PHP process.
- Web restoration supports the declared same-site URL/table-prefix contract. It retains destination connection settings and the running manager, then applies an audited bootstrap change to wp-config.php. It is not a verified arbitrary cross-domain migration engine. Standard single-site principal tables and supported InnoDB schemas are required; custom principal tables, unknown inbound user-table dependencies and multisite are refused.
- Caught exceptions can trigger rollback. Fatal PHP termination, exhausted process memory, hard timeout, container kill, power loss, database outage or disk failure can interrupt mutation and cannot be represented as automatically recovered. Keep the encrypted rollback image, maintenance procedure and operator recovery instructions available.
- Source quiescence must include scheduled jobs, queues, external writers and offloaded services. A transaction gives an InnoDB database snapshot; it does not create an atomic snapshot of all website files and all external systems.
- Plaintext staging on private disk is needed to validate before restore. Normal cleanup is not secure erasure of filesystem blocks or snapshots. Sensitive hosting requires encrypted disks and suitable server backup/retention controls.
- Restrictive filesystem/database support should fail clearly on unsupported cases. Do not broaden these constraints or mark arbitrary hosting layouts complete without targeted tests.
- Public applications requiring WordPress login, REST, admin-ajax, direct PHP endpoints, public cron, GraphQL or custom write methods need a separately qualified application adapter. GET/HEAD and ordinary front-controller POST support does not prove every plugin-powered frontend remains functional. Read-only container site mounts also require explicit design for application file writes.
- Application code cannot remove provider/root, filesystem, database-server, hypervisor or account-owner infrastructure privileges. Deleting a WordPress administrator is not revocation of SSH/hosting access, and a restart policy cannot guarantee uptime.
- Private configuration modes and host/container PHP worker ownership/ACLs must agree; do not widen all wp-config files to world-readable merely to make a container start.
